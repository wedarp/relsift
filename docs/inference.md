# 函数依赖推导与规则审查

发现和推导回答两类问题。发现读取表快照，返回当前行中成立的最小依赖。`wedarp/relsift/inference` 接收一组声明的依赖，计算这些前提在逻辑上蕴含哪些结论。可以把人工确认的规则作为前提，也可以把快照规则作为实验前提。推导的结论继承前提的适用范围。使用截断的发现报告时，推导仅针对报告中提供的规则。

## 从两条规则推导

```sh
moon run examples/inference
```

示例声明 `{order_id, line_no} → product_id` 和 `product_id → product_name`。查询 `{order_id, line_no} → product_name` 得到两步证明。第一步用第 0 条前提得到 `product_id`，第二步用第 1 条前提得到 `product_name`。查询同一组合能否决定 `warehouse` 时，例子给出一个反模型，两行可以有相同订单、行号、商品和商品名，同时所属仓库不同。见 [完整源码](../examples/inference/main.mbt)。

同一个示例从四行订单发现 8 条 FD，将它们精简为 5 条等价规则。独立审查确认双向蕴含、没有可删的整条规则，也没有可移除的左侧列。按这一规则集推导出 5 个最小决定列组。把第一行完整复制一次，5 个列组仍能决定全表属性，但实际行唯一性检查全部失败。

## 输入和返回契约

- `theory(columns, rules)` 以非空、无重复的字符串列 ID 编译规则，每个 `Rule` 有单属性右侧。允许空左侧表示常量依赖。拒绝未知列、重复左侧列、平凡规则和重复前提。列 ID 按字面精确匹配。`rules()` 返回副本，前提索引始终对应编译时规则的原始顺序。
- `Theory::closure(seeds, limits?)` 求属性闭包。种子和可证属性按字面排序，证明步骤按推导顺序排列。每步持有前提索引和新增属性。`verify_trace` 按前提独立重放步骤，并核对返回属性。它只证明记录下来的推导有效，完整性需要检查搜索状态。
- `Theory::explain(result, target)` 从一份可复核的闭包记录提取目标所依赖的步骤。若目标是种子，返回空证明。若记录中没有目标，返回 `None`。证明选择由原始推导顺序决定，可能存在步数更少的其他证明。
- `Theory::implies(lhs, rhs, limits?)` 返回 `Entailed(proof)`、`Refuted(agreement)` 或 `Undetermined`。可分别用 `verify_entailment` 和 `verify_counterexample` 独立检查正反证据。`Entailed` 在部分状态下仍成立，因为已有证明。`Refuted` 只在闭包完成后产生。非法输入通过 `model.InputError` 报告。

## 算法和预算

编译阶段按列记录引用该列的前提。查询先将种子和常量依赖得出的属性入队，每取出一个新属性就更新相关前提尚缺的列数。计数首次到零时可以应用该前提。队列中的列和被触发的前提各访问一次，搜索工作量取决于模式大小、前提数量和被触及的左侧列引用数。最终对属性集合排序。编译结果可复用于多次查询。

若闭包不含目标，可构造两行。第一行在所有列取 `0`，第二行仅在闭包中的列取 `0`，其他列取 `1`。凡两行在前提左侧相等，该前提右侧也属于闭包，因而两行满足全部前提。它们在查询的左侧相等、右侧不同，足以反驳逻辑蕴含。`Refuted` 以相等列集合表示这两行，可用 `verify_counterexample` 逐条检查前提。反模型中的行是逻辑构造，业务表中可能从未出现。

闭包查询单独计费。`max_candidates` 限制前提触发次数，包含右侧已知的前提。`max_results` 限制新增属性数量，种子不占限额。`max_work` 覆盖查询初始化、队列访问和前提引用更新；种子与输出整理、证据提取和独立复核在计费之外。分区、缓存计数均为零，`max_lhs`、`max_ucc_width` 不限制推导所接受的前提宽度。`CompleteInDomain` 表示对这组前提的闭包已完成，`Partial` 表示保留已证属性及推导步骤。这些计数无法代替进程资源限额。

## 精简和比较规则集

`Theory::minimal_cover` 先逐列试删左侧，再逐条试删规则。每次缩短都要求原规则集能推出缩短后的规则，每次整条移除都要求剩余规则可以推出该规则。排序后的列 ID 和规则使操作顺序可复现，`edits` 记录每一次已应用的删减。相同输入集合可有多种最小覆盖。此处的最小性指左侧列和整条规则均不可再删，输出规则总条数未必是所有等价表示中最少的。常量依赖允许保有空左侧。

单属性右侧、外余列和最小覆盖采用 Elmasri 与 Navathe 所述的定义。 [《Fundamentals of Database Systems》第 15 章](https://eecs.csuohio.edu/~sschung/cis430/Fundamentals-of-Database-Systems-Pearson-2015-Ramez-Elmasri-Shamkant-B.-Navathe.pdf)

`Theory::compare(other)` 检查左右规则集的双向蕴含，要求列 ID 集合一致。每个方向返回 `EntailsAll`、`Separated` 或 `Unchecked`。差异报告只取目标规则顺序中的第一条无法推出的规则，并给出源规则集的两行反模型。用 `source.verify_separation(target, witness)` 检查目标规则归属和反模型。列名相同即进入逻辑比较，业务口径变更需要由调用者判断。

`original.audit_cover(candidate)` 使用独立的固定点扫描，先运行双向比较，再检查候选规则的左侧和规则集合是否不可再删。只有两个方向均为 `EntailsAll`、最小性为 `Irreducible` 才确认最小覆盖。若发现可删项，`Reducible` 给出规则索引、可选的删列 ID 和推导过程，可用 `candidate.verify_reduction` 复核。完整状态表示相关判定已经得出，包括发现不等价或可删项的情况。

覆盖生成的 `max_candidates` 按试删计数，`max_results` 按已提交的删减计数。若生成中途耗尽预算，返回的规则仍与输入等价，最小性尚待确认。比较和覆盖审查按待检验规则或试删计候选，按返回的反模型或删减证明计结果，审查在各阶段共享预算。未完成的部分保留 `Unchecked` 或 `MinimalityUnchecked`。工作量覆盖主要索引、扫描和删减步骤；排序及返回对象整理可能另有开销。

## 从规则推导最小决定列组

`Theory::schema_keys` 按宽度列举闭包包含全部模式列的最小集合。这相当于集合语义下从已声明 FD 推导候选键。应用在原始导出时，还应调用 `verify.unique` 检查实际重数。输入规则来自宽度受限或中断的发现报告时，计算结果只针对其中已有的规则。

任何从未出现在右侧的列都必须加入候选。先求这些必需列的闭包，排除已经能决定的扩展列，再按宽度搜索并剪去已证最小组合的超集。返回的每个列组附带正向闭包推导，以及删除任一列后无法决定某个属性的两行反模型。`verify_schema_key` 直接重放推导并分项验证反模型。

`max_lhs` 定义最大列组宽度，`max_candidates` 与 `max_results` 分别限制访问组合数和已证列组数。预算耗尽时只保留具有完整证据的结果。空模式或全由常量依赖推出的模式可以返回空集合；没有前提的非空模式只有全列组决定全部属性。所有计算都在声明域内完成时，`CompleteInDomain` 才可用来解释零结果。最坏情况下仍需枚举指数规模的列子集。
